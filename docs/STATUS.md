  Проверяются MOQ/кратность, коды/артикулы, единицы и связь остатка с резервом.

- Источник продаж выбирается по SKU и диапазону месяцев. Частное правило
  имеет приоритет над общим; неоднозначные пересечения отклоняются. Выбранный
  источник не заменяется другим при пропуске. Несогласованные решения должны
  быть явно помечены как `scenario`.
- Положительный путь требует полной ETA для каждой исходной строки и явной
  единицы пути. Если путь уже в учётной единице, повторного перевода нет.
  Отсутствие открытых заказов требует `no_open_orders`; пустота не равна нулю.
- Добавлены три статуса и причины по каждому SKU. Входной контроль
  `calculation_input` отклоняет неполные данные, а сценарий допускает только
  с явным `allow_scenario=True`. Выбранная отрицательная строка, даже внутри
  положительной суммы, остаётся блокирующей до обработки возвратов на этапе 6.
- SQLite обновлена до схемы 4: отдельные версии конфигураций, проверок,
  выбранных продаж, диагностик и статусов. Повтор того же запуска переиспользует
  результат; изменение параметров/правил/кода создаёт новый. Исходные факты и
  старые решения не переписываются. Прогноз или заказ пока не создаётся.
- В UI добавлены сохранение настройки, запуск/выбор проверки, фильтр SKU,

## Результат этапа 9

- Добавлено независимое от UI расчётное ядро и итоговая схема SQLite 8.
  `replenishment_runs` хранит точные входы, версии качества и
  подготовки, отпечаток правил/кода и итог; `replenishment_items` хранит
  результаты по SKU. Повторный запуск одинакового сценария возвращает тот же
  `run_id`; отчёт по ID читает сохранённый результат.
- Дата расчёта обязательна и сверяется с `as_of` обеих версий. Для имеющегося
  реального набора она **2026-09-22**; дата системы не подставляется. Отдельный
  синтетический набор имеет собственную дату `2026-01-01`.
- На один SKU используются проверенный физический остаток и резерв, политика,
  L/R, единицы и ограничения, а также подготовленная история того же снимка.
  Основной вход — совместимый `forecast_run_id` этапа 8. Ручной прогноз содержит
  собственную версию/источник и остаётся сценарным fallback; ошибка одного SKU
  сохраняется как `blocked` и не отменяет остальные.
- Формула включает регулярный прогноз, незарезервированные текущие проектные
  обязательства, страховой запас в днях, доступный остаток и своевременные
  поступления. Резерв вычитается один раз. Исторические исключённые проекты и
  оценённые прошлые потери не становятся текущим долгом автоматически.
- Календарь показывает спрос и поступления по дням, остаток с новым заказом и
  без него, первую дату риска и отдельный срочный дефицит до обычного ETA.
  Просроченные поступления исключаются; отсутствие подтверждённой ETA блокирует
  полный расчёт строки. Месячный прогноз равномерно распределяется по дням,
  поэтому соответствующая дата риска отмечена как приблизительная.
- Потребность сначала переводится в закупочную единицу, затем применяется MOQ
  и кратность. При нулевой потребности заказ равен нулю. При неизвестном
  ограничении выдаётся `incomplete_constraints`; отдельный MOQ из кратности не
  придумывается. Объяснение хранит компоненты, единицы, источники, допущения,
  влияние округления и текст из тех же чисел.
- CLI: `replenish --file ПУТЬ.json` и `replenishment-report --run ID [--sku SKU]`.

## Результат этапа 8

- Добавлены чистое ядро `hackalem.domain.forecasting`, версионированный сервис,
  миграция прогноза в единой схеме 7, CLI и отдельная панель Streamlit. Прогноз связан с точными
  версиями качества/очистки, SKU, датой среза, кодом и настройкой; повтор тех же
  входов возвращает прежний ID.
- Сравниваются сезонный аналог, сглаженный уровень с ограниченным затухающим
  трендом и Croston SBA. Baseline: последний месяц, среднее трёх месяцев и
  календарный месяц прошлого года. Отчёт показывает WAPE, MAE в единицах SKU,
  signed bias и измеренную разницу с лучшим baseline.
- Внешние rolling-origin точки используют только прошлое. Для каждой точки
  документы обрезаются до origin, автоматическая очистка запускается снова,
  параметры Holt/Croston подбираются внутри обучающей части. Финальная модель
  переобучается на всех завершённых месяцах.
- Текущий месяц исключён. При срезе 22.09.2026 ожидается история не позже августа
  и прогноз с сентября; разрыв не заменяется нулём. Охват `source_report`
  сохраняется явно, складской фильтр не выдуман.
- Бизнес-прирост получил отдельные период, охват и режим `replace_trend` либо
  `additional`; в месяце он применяется максимум один раз. Для короткой истории
  нужен явный fallback совпадающей категории или сценария, а отсутствие fallback
  даёт статус «Не хватает данных» без числового прогноза.
- Неустановленные сезонные агрегаты нельзя включить в количественный прогноз;
  решение об исключении видно в отчёте. Синтетическая истина недоступна модели
  и читается только командой `forecast-evaluate`.
- Совместимая версия этапа 7 теперь входит в обучающую историю с проверкой
  снимка, SKU и даты; историческая поправка не становится текущим backlog.
  Без неё отчёт явно фиксирует ограничение. Прогноз не является утверждением.

Для возврата к реальной базе после остановки приложения установите
`$env:HACKALEM_DATA_DIR = '.local'` либо свой прежний путь. Подробный протокол
и ожидающие проверки: `docs/SYNTHETIC_DATA.md`.

Следующий незавершённый этап — **12: итоговая проверка кейса и демонстрация**.
Контракты импортов описаны в `docs/IMPORT_SYSTEME.md` и
`docs/IMPORT_IEK.md`, согласование — в `docs/DATA_CONTRACT.md`.
Общий API импорта — `hackalem.services.imports`; входы будущего прогноза
должны проходить через шлюз качества `hackalem.services.cleaning.prepared_input`
и, где доказано отсутствие, использовать обучающую историю
`hackalem.services.lost_demand.adjusted_history` того же снимка и даты.

Реальные данные обоих поставщиков загружены и сверены. Актуальные бизнес-условия
должен подтвердить пользователь; сейчас ни один реальный SKU не допущен к
подтверждённому расчёту. Ввод параметров пока через JSON, охват выбранной истории
ограничен целым отчётом по SKU/месяцу без фильтра складов. Синтетический
проверочный бизнес-набор создан отдельно; он не доказывает точность на реальном
бизнесе. Оценка упущенного спроса на реальных данных без полнодневного
журнала недоступна; ручные интервалы остаются сценарием. Прогноз без версии
этапа 7 работает с явным ограничением. Пополнение принимает сохранённый прогноз
этапа 8 либо явно сценарный ручной прогноз. Интерфейс рекомендаций, проекты,
локальное утверждение и проверяемый экспорт реализованы. Форматы расчёта и
заказа описаны в `docs/REPLENISHMENT.md` и `docs/ORDERS.md`.
Подтверждение единиц и статус готовности входов не являются утверждением заказа.

Исходные замечания сохраняются: нельзя использовать AP/AQ как готовый прогноз,
считать BB Systeme существующим заказом, повторно вычитать резерв из AZ,
назначать год частичной ETA или считать начальный месячный остаток IEK
текущим. Архивные цены/MOQ не активированы; актуальные условия и подтверждённые
единицы пути необходимо согласовать до реального расчёта закупок.

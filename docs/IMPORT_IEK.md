# Технический контракт импорта IEK — этап 3

Этап добавляет импорт IEK, извлечение встроенного архивного прайса и отдельные сведения о единицах. Он не согласует противоречащие продажи, не выбирает действующие условия поставщика и не рассчитывает прогноз или заказ. Фактические результаты проверок ведутся в `docs/STATUS.md`.

## Вход и снимок

Публичный API — `hackalem.services.imports.import_iek(Settings)`. Источники читаются из `HACKALEM_SOURCE_DIR/IEK`; временные файлы Excel `~$...` пропускаются. Нужен ровно один XLSX каждого типа:

| `source_kind` | Извлекаемые данные |
|---|---|
| `minimums` | Товары, артикулы и «Мин. разр. к отгр.»; встроенный внешний прайс при его наличии |
| `transactions` | Каждая строка документа: дата, номер, вид, SKU, единица, склад, количество |
| `monthly_stock` | Начальные месячные остатки; `monthly_values.series = opening_stock` |
| `monthly_sales` | Месячные количества; `monthly_values.series = sales` |
| `seasonality` | Исходные агрегаты «год × месяц», отдельно от спроса конкретного SKU |
| `incoming` | Количества по заказам из отдельных колонок, номер и дата заказа, срок «поступление до» |

`hackalem.importers.iek.parse_workbook(Path) -> ParsedIEKWorkbook` определяет тип по заголовкам в первых 12 строках, а не имени. Для начальных остатков дополнительно требуется подпись «нач. остаток». Полная дата имени файла используется только как `snapshot_date` источника `incoming`. Обещанный срок поступления извлекается отдельно из заголовка колонки и не считается фактической датой приёмки или сроком нового заказа.

Снимок имеет `supplier = IEK` и содержит ровно по одной версии шести типов. Версии другого поставщика нельзя включить в этот набор. Типовые заголовки динамики одинаковы у IEK и Systeme: поставщик задаётся профилем импорта, а не угадывается по такой таблице.

Импорт читает зафиксированные bytes через временные рабочие копии. Исходники не пересохраняются, формулы не пересчитываются. Неизвестный основной шаблон, повтор типа или неполный набор отменяют новый импорт целиком; проблемы отдельных ячеек сохраняются без потери независимых корректных строк. Повтор неизменного набора переиспользует версии и снимок при совпадении кода и параметров. Старые снимки не изменяются и не складываются с новыми.

Версия правил — `iek-1`. Версия парсера учитывает код `iek.py`, `iek_cache.py` и общие средства `systeme.py`. Хранилище сохраняет хэши bytes, имя и путь, время импорта UTC, правила, код и параметры. Для IEK фиксируются `calculation_version = not-implemented-stage-3`, `sales_authority = null`, `archive_terms_active = false`; смена этих правил через дополнительные параметры импорта не разрешает неподдерживаемый расчёт.

## Факты и происхождение

Общий контракт ячеек и фактов описан в `IMPORT_SYSTEME.md`. `ParsedIEKWorkbook` расширяет его следующими списками; при сохранении SQLite добавляет `file_id`:

| Список / таблица | Основные поля |
|---|---|
| `incoming_orders` | `sheet`, `row`, `sku`, `article`, `order_number`, `order_date`, `eta_deadline`, `quantity`, `state`, `unit`, `cell`, `header_cell` |
| `catalog_items` | Артикул и название, категория и три уровня группировки, закупочная единица, NTIN, статус, тара, количество в таре, кратность, минимум, базовая цена, валюта, дата, `states_json`, происхождение |
| `external_sources` | `sheet`, `xml_path`, исходный `external_target`, `price_date`, `status` |
| `row_metadata` | `sheet`, физический `row`, `hidden` (`0` или `1`), включая скрытые пустые строки |

Коды SKU, артикулы и номера документов остаются строками. Одинаковые документы в разных физических строках не удаляются. `products` содержит первое вхождение SKU на листе, а все повторяющиеся факты и исходные строки сохраняются. Повторяющиеся артикулы прайса также остаются отдельными строками.

| `state` | Представление |
|---|---|
| `value` | Распознанное значение, включая явный ноль и отрицательное количество |
| `blank` | Отсутствующее значение; число `None` / SQL `NULL`, без подстановки нуля или единицы |
| `error` | Сохранённая ошибка Excel, отсутствующий результат формулы или неподходящее числовое значение; нормализованное число `None` / `NULL` |

Отрицательные количества сохраняются с предупреждением и не объявляются автоматически выбросом или возвратом. XML-тип `e` без самого значения не создаёт выдуманную ошибку: это пустая ячейка. Явный текстовый маркер «(пусто)» в числовом поле прайса даёт `blank` и предупреждение; исходный текст остаётся доступен.

`source_rows.cells_json` хранит по буквам столбцов `value`, `formula`, `data_type`, `number_format`; ошибки могут иметь `cached_error`. Значение формулы берётся только из сохранённого кэша. Объявленный XML dimension не ограничивает чтение; фактические размеры сохраняются отдельно. Все листы читаются независимо от видимости, скрытые строки не исключаются.

Месячный «Итого» остатков сохраняется как `reported_opening_stock_total`, а не как текущий запас или сумма запасов по месяцам. Минимум отгрузки из MOQ сохраняется как `minimum_order`, отдельно от `order_multiple`. Неизвестный минимум не становится единицей. У пути нет подтверждённой единицы количества: `incoming_orders.unit` остаётся `None`; примечание в названии сохраняется, но само по себе не разрешает конвертацию. Служебные строки пути с кодами `0`/`1` остаются в исходных данных и не создают товары.

## Архивный внешний прайс

`append_external_cache(path, result)` читает только ZIP-члены `xl/externalLinks/*.xml` и их relationships. Адрес внешнего файла хранится как метаданные; он никогда не открывается локально или по сети. Внешние ссылки Excel не обновляются.

В исходном MOQ представлены три псевдолиста:

- `externalLink1.xml/Прайс` — строки каталога;
- `externalLink1.xml/Установите свою скидку` — пустой кэш;
- `externalLink1.xml/Акция` — пустой кэш.

Каждый получает `state = external_cache` и запись `external_sources.status = archived_external_cache`. Префикс имени XML отличает одноимённые листы разных внешних ссылок. В XML нет объявленного dimension: `declared_dimension = None`, размеры определяются по фактическим координатам. Пустые внешние листы сохраняются как метаданные без придуманных строк.

Каталог определяется по заголовкам. Четыре числовых поля — `pack_quantity`, `order_multiple`, `minimum_order`, `base_price` — имеют собственные состояния в JSON-строке `states_json`. `catalog_items.cell` указывает на ячейку артикула; исходная строка сохраняет остальные поля, поэтому цену или минимум можно проверить по их собственным координатам.

Валюта KZT назначается только при явном слове «тенге» в заголовке цены. Дата извлекается из полной однозначной даты имени внешнего target; у данного архива это `2026-08-03`. Отсутствующие дата или валюта остаются `None`. Базовая цена архивного прайса не объявляется закупочной ценой компании, а условия прайса не становятся действующими автоматически.

## Единицы и подтверждения

SQLite версии 3 добавляет `unit_assessments` и `unit_confirmations`, связанные со снимком и SKU. При создании снимка IEK сохраняется отдельная оценка единиц: исходные учётные единицы, артикулы, совпадения архивного каталога, наблюдения MOQ, статус и возможный `proposed_factor`. Это диагностика импорта, а не разрешение применить архивный прайс.

Возможные статусы: `accounting_unit_conflict`, `accounting_unit_missing`, `catalog_match_missing_or_ambiguous`, `purchase_unit_missing`, `conversion_confirmation_required`, `archive_units_unconfirmed`. Коэффициент может предлагаться по совпадающим единицам или явной подсказке вида «4 шт/компл» в названии. Даже предложенный коэффициент `1` остаётся неподтверждённым.

- `get_unit_assessment(database_path, snapshot_id, sku)` возвращает оценку, доказательства и историю подтверждений.
- `confirm_unit_conversion(...)` требует положительный конечный коэффициент, `archive_units_confirmed=True`, основание и автора. Единицы должны быть известны и однозначны. Создаётся новая запись; исходная оценка не переписывается.
- `convert_quantity(..., confirmation_id=...)` принимает только подтверждение того же снимка и SKU и переводит закупочное количество в учётное: `accounting_quantity = purchase_quantity × factor`.

**Подтверждение относится только к применимости единиц и коэффициенту. Оно не активирует архивные MOQ, кратность или цену.** `archive_terms_active` остаётся `false`, а ответ конвертации содержит `archive_prices_and_moq_active = false`. Старое подтверждение нельзя перенести на новый снимок или другой SKU. CLI `units` только показывает сведения; он не выполняет подтверждение и не меняет количество.

## Чтение и команды

Публичные функции чтения доступны через `hackalem.services.imports`. `read_records(...)` требует явного снимка, типа источника и таблицы; каталог фильтруется по `article`, поскольку внутреннего SKU в нём нет. `trace_cell(...)` возвращает исходную ячейку, нормализованные записи, проблемы, видимость физической строки и метаданные внешнего источника, если применимо.

Команды выполняются из корня проекта. В примерах замените `N` на ID нужного снимка IEK из `list-snapshots`; номер не фиксирован заранее.

```powershell
uv run --locked python -m hackalem import-iek
uv run --locked python -m hackalem list-snapshots
uv run --locked python -m hackalem report --snapshot N
uv run --locked python -m hackalem units --snapshot N --sku 280200087_
uv run --locked python -m hackalem trace --snapshot N --source minimums --sheet "Лист7" --cell E2
uv run --locked python -m hackalem trace --snapshot N --source minimums --sheet "externalLink1.xml/Прайс" --cell O8146
uv run --locked python -m hackalem trace --snapshot N --source incoming --sheet "Лист4" --cell D1
```

Команды выводят JSON UTF-8; ошибка возвращает сообщение в stderr и код завершения 1. Отчёт и диагностика единиц не заменяют следующий этап согласования источников. Действующие условия поставщика, актуальный доступный запас, правила продаж и бизнес-параметры остаются отдельными задачами.

# Расчёт пополнения: этап 9

Расчёт запускается без интерфейса и сохраняется в SQLite под `run_id`. Он принимает
неизменяемые версии проверки качества и подготовки регулярного спроса одного
снимка. Основной вход — сохранённый `forecast_run_id` этапа 8. Ручной прогноз
поддерживается как явно сценарный fallback. Расчёт не утверждает и не отправляет
заказ поставщику.

## Деловая дата и вход

Для существующих реальных файлов дата среза — **2026-09-22**. Её нужно указать
явно; текущая дата компьютера не подставляется. Версии качества и подготовки
должны иметь тот же `snapshot_id` и `as_of`. Синтетический проверочный набор
имеет другой срез — `2026-01-01`; его нельзя выдавать за реальный срез.

Файл UTF-8 для `replenish --file` имеет форму:

```json
{
  "quality_run_id": 1,
  "cleaning_run_id": 1,
  "as_of": "2026-09-22",
  "supplier": "Systeme Electric",
  "warehouse": "all_selected_warehouses",
  "items": [
    {
      "sku": "ВАШ-SKU",
      "category_code": "ВАША-КАТЕГОРИЯ",
      "forecast_run_id": 1,
      "project_commitments": []
    }
  ]
}
```

Прогноз проверяется по `snapshot_id`, `quality_run_id`, `cleaning_run_id`, SKU,
дате среза и единице. Месячные точки из сохранённого прогноза равномерно
распределяются по календарным дням. Если сохранённого прогноза нет, вместо
`forecast_run_id` разрешён ручной сценарный объект:

```json
{
  "forecast": {
        "basis": "regular_unreserved",
        "version": "manual-scenario-1",
        "source": "план закупщика",
        "author": "имя автора",
        "reason": "основание сценарного прогноза",
        "granularity": "monthly",
        "unit": "шт",
        "values": [
          {"period": "2026-09-01", "quantity": 300},
          {"period": "2026-10-01", "quantity": 310}
        ],
        "adjustments": []
  }
}
```

Сценарий из интерфейса копирует неизменяемые входы базового расчёта и добавляет
верхнеуровневый объект `scenario` с `base_run_id`, коэффициентом
`demand_factor`, задержкой `arrival_delay_days`, автором и основанием. Сервис
проверяет, что базовый `run_id` относится к тем же снимку, версиям, дате и
товарам. Коэффициент применяется к точкам прогноза, задержка — к подтверждённым
ETA; результат получает новый `run_id`, а базовый расчёт не изменяется.

Номера версий, SKU, категория, единица, прогноз и период покрытия в примере
служат образцом формы; замените их проверенными значениями своего снимка.
Прогноз должен покрывать **каждый день** горизонта `L+R`. Для `monthly`
количество полного календарного месяца равномерно делится на число его дней.
Горизонт MVP ограничен 730 днями.
Поэтому дата риска приблизительна, даже если в календаре показан конкретный
день. Для `daily` подайте отдельную запись `{ "date": "YYYY-MM-DD",
"quantity": число }` на каждый день. `adjustments` — уже включённый в
переданные значения вклад корректировок для объяснения; расчёт не применяет
его повторно и не добавляет настройку роста второй раз.

Пока поддерживается только весь выбранный охват исходного отчёта:
`warehouse=all_selected_warehouses`. Фильтр отдельного склада не имитируется.
Поставщик и категория сверяются с версиями качества. Негодный SKU получает
`blocked` со своей причиной, а независимые SKU продолжают рассчитываться.

Текущие проектные обязательства передаются отдельно от регулярного прогноза:

```json
{"due": "2026-10-03", "quantity": 20, "reservation": "unreserved", "source": "проектный договор №…"}
```

Для уже включённого в физический резерв обязательства укажите
`reservation=already_reserved`: оно не добавится к спросу снова. Прогноз
должен исключать текущие резервы (`basis=regular_unreserved`). Исторически
исключённая разовая сделка не превращается автоматически в текущий долг.

## Формула и календарь

Все потребности сначала считаются в учётной единице:

`max(0, регулярный прогноз на L+R + незарезервированные проектные обязательства
+ страховой запас − (физический остаток − резерв) − своевременные поступления)`.

Подтверждённые поступления распределяются по ETA. Просроченные и не имеющие
подтверждённой ETA не считаются прибывшими. Неподтверждённая ETA блокирует
полный расчёт SKU; просроченная подтверждённая ETA исключается из суммы и
остаётся видимой в `excluded_arrivals`. Страховой запас MVP = средний дневной
прогноз на горизонте × `safety_days`; это допущение, не статистический уровень
сервиса. В режиме `on_demand` страховой запас равен нулю; `exclude` блокирует
товар.

Полученная потребность делится на подтверждённый `unit_factor` — число учётных
единиц в одной закупочной. Только затем применяется `MOQ` и кратность:
`P × ceil(max(Q_raw, M) / P)`. Нулевая потребность даёт нулевой заказ при любом
MOQ. Если известна только кратность, отдельный минимум не выдумывается;
результат помечается `incomplete_constraints`. Если кратность неизвестна,
итоговая закупочная величина не выдаётся. Ручной прогноз, синтетический набор
или любой сценарный вход сохраняют сценарный статус. Расчётный прогноз этапа 8
не означает утверждение заказа человеком.

Календарь содержит ежедневные спрос, отдельное проектное обязательство,
существующие поступления, прибытие предлагаемого нового заказа, остаток с ним
и без него. `urgent_risk_date` показывает дефицит до обычной даты новой
поставки; это отдельная срочная проблема, которую обычное округление заказа
не устраняет. Структурированное `explanation` содержит компоненты формулы,
единицы, версии, источники, допущения, ограничения, влияние округления и
точность даты риска; `text` составляется из тех же чисел.

## Запуск и ручная сверка

```powershell
uv run --locked python -m hackalem replenish --file .\my_replenishment.json
uv run --locked python -m hackalem replenishment-report --run 1 --sku ВАШ-SKU
```

Повторный запуск с теми же входами и версией правил возвращает тот же `run_id`.
Отчёт по нему читает сохранённые результаты, а не пересчитывает их на новых
данных. Для ручной сверки сопоставьте `physical_stock − reserved_stock` с
`available_stock`, просуммируйте `calendar` и `arrivals`, повторите формулу,
затем разделите `raw_need_accounting` на `unit_factor` и проверьте округление.

Проверочные примеры в `tests/test_replenishment.py`: `300+60−90−100=170`,
кратность 12 → 180; нулевой спрос не вызывает MOQ-заказ; резерв не вычитается
дважды; задержка меняет срочность; 5 комплектов × 4 = 20 штук.

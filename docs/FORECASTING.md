# Прогноз регулярного спроса — этап 8

## Граница этапа

Прогноз строится для одного SKU, снимка и охвата `source_report`. Он принимает
только совместимые версии проверки качества и подготовки регулярного спроса
через `prepared_input`. Результат не является заказом и не утверждается.

Этап 7 не реализован. Поэтому прогноз использует очищенные наблюдаемые продажи,
но не восстанавливает цензурированный спрос при stockout. Это ограничение
сохраняется в каждом отчёте; преимущество на реальных цензурированных продажах
не заявляется.

## Модели и временная проверка

Сравниваются три небольшие модели:

- `seasonal_analog` — тот же календарный месяц прошлого года;
- `damped_level_trend` — сглаженный уровень и ограниченный затухающий тренд;
- `intermittent_sba` — метод Croston с поправкой SBA для прерывистого спроса.

Baseline: последний завершённый месяц, среднее трёх завершённых месяцев и тот
же месяц прошлого года. Выбор модели выполняется по последовательным
одношаговым rolling-origin проверкам, максимум по последним 12 точкам. WAPE,
MAE в учётных единицах и signed bias показываются отдельно. Преимущество над
baseline отмечается только при измеренной отрицательной разнице WAPE.

Для каждого внешнего origin документы обрезаются по времени, автоматическая
очистка этапа 6 запускается заново, а параметры Holt/Croston подбираются только
на обучающей части. Синтетический `validation/truth.json` недоступен этому
коду; его читает только отдельная команда оценки.

Текущий месяц исключён полностью. Например, при срезе 22.09.2026 последним
месяцем месячного обучения должен быть август, а прогноз начинается с
01.09.2026. Разрыв истории не заполняется нулём.

## Настройка

Команда принимает JSON с пятью разделами:

```json
{
  "horizon_months": 12,
  "warehouse_scope": "source_report",
  "growth_application": {
    "mode": "replace_trend",
    "start": "2026-09-01",
    "end": "2027-08-01",
    "scope": "source_report",
    "status": "confirmed",
    "reason": "Согласованный плановый прирост на период",
    "author": "Ответственный сотрудник"
  },
  "short_history_fallback": null,
  "seasonal_aggregate_policy": {
    "use": false,
    "unit_status": "unknown",
    "reason": "Единица и связь агрегата с SKU не подтверждены",
    "author": "Ответственный сотрудник"
  }
}
```

Число прироста берётся из версионированного параметра `business_growth`.
`replace_trend` исключает трендовую модель при ненулевом бизнес-приросте;
`additional` явно разрешает применить прирост поверх выбранной статистической
модели. В обоих случаях множитель применяется к месяцу ровно один раз и только
в заданном периоде.

Для истории короче 12 месяцев прогноз без fallback сохраняет статус
«Не хватает данных». Явный fallback имеет вид:

```json
{
  "category_code": "CONFIRMED-CATEGORY",
  "monthly_demand": 120,
  "status": "scenario",
  "reason": "Сценарный уровень для новинки",
  "author": "Ответственный сотрудник"
}
```

Код должен совпадать с категорией SKU. Отчёт показывает, что такой прогноз не
прошёл историческое сравнение, и не заявляет превосходство модели.

Сезонные агрегаты исходных книг пока имеют неизвестную единицу и не связаны с
конкретным SKU. Настройка обязана фиксировать их исключение; включить их как
коэффициент количественного спроса нельзя.

## CLI

```powershell
uv run --locked python -m hackalem forecast `
  --quality-run 2 --cleaning-run 1 --sku 130200305_ `
  --config .local/forecast.json
uv run --locked python -m hackalem forecast-runs --snapshot 2 --sku 130200305_
uv run --locked python -m hackalem forecast-report --run 1
```

Для синтетики нужен явный `--allow-scenario`. Проверка oracle выполняется
отдельно, номера относятся к базе выбранного dataset:

```powershell
uv run --locked python -m hackalem forecast-evaluate `
  --dataset .local/synthetic/synthetic-1-seed-20260923 `
  --runs 1 2 3
```

Каждая версия хранит входные run ID, SKU, настройку, версии правил/кода,
выбранную модель, backtest-точки, будущие значения, ограничения и происхождение
решений. Повтор идентичных входов возвращает прежний ID.
